## 1. 背景と目的

mkb-readerは完成後の利用が低調である。原因は、モバイル閲覧を想定しながらファイルの投入・整理がモバイルでは億劫であること。実体をフラン上に置き、整理はPC（エクスプローラ）で完結させ、閲覧はPixel 10からTailscale経由で行う体制に転換する。

同時に、書庫を以下の役割を持つ**共有アーカイブ層**として位置づける。

1. 人間にとって美的に読める場（mkb本来の読書体験）
2. 機械にとって身近に読める場（変換・蒸留済み成果物の配架先。将来のread_library接続を考慮）
3. 電子書籍・PDF・txt等の保管場所（形式不問）

記憶アーキテクチャ上の位置: **変化する蒸留記憶はNotion、原文・成果物アーカイブは書庫**。索引と実体の分離。不変性の保証はGitHub（git化バックアップ）が担い、書庫自体は発注者の編集（将来のmkb-reader編集機能）を受け入れる。

## 2. 構成（案B・chat-pwa方式）

```
[Pixel 10 / mkb-reader PWA] ⇄ tailscale serve (https, *.ts.net)
                                   ⇄ [フラン: 書庫サーバ (Node.js + Express)]
                                        ├ mkb-reader ビルド済み配信（同一オリジン）
                                        ├ 索引JSON生成・配信
                                        ├ 実体配信（全形式）
                                        └ 保存API（PUT/POST）
                                   [書庫ディレクトリ] ＝ ローカルgitリポジトリ（private）
```

- 同一オリジン配信によりCORS・混在コンテンツ問題を構造的に排除
- GitHub Pages版は併存（ローカル保存のみの従来モード。廃止しない）
- 実体・設定はすべてフランのローカル。Tailscaleは暗号化された呼び出し経路のみ

## 3. 機能要件

### F-1 書庫サーバ
- 指定ディレクトリ（.envでパス設定）を書庫として配信
- 起動時＋変更検知（または再スキャンAPI）で索引JSONを生成
- 索引メタデータ: ファイル名・kind（mkb/text/md/pdf/epub/image/other）・題名・日付・タグ・分冊構成（mkbのみ）・サイズ・更新日時
- 実体配信: 全形式。Content-Type適切付与
- 保存API: 汎用ファイル保存（PUT）。mkb-readerからの保存し直し・変換成果物の配架を受ける
- mkb-readerビルド済み成果物の同一オリジン配信

### F-2 棚の分離（P-3適用・前提事項）
- 書庫直下を**公開棚/私室棚**のディレクトリで分離
- サーバの配信・索引スコープは公開棚のみ（コード許可リストではなく、サーバのルート設定で物理制御）
- 私室棚はgitリポジトリ外・索引外。バックアップ経路は別途（残課題として記帳）

### F-3 mkb-reader リモート書庫モード
- 書庫一覧表示（索引JSON由来。題名・kind・タグ・日付）
- mkb: 従来どおりの読書体験（縦書き含む）
- txt/md/画像: リーダー内表示
- pdf/epub/other: 端末ビューアへ受け渡し（リーダー内表示は将来工事に切り分け）
- 既存ローカル保存機能は維持。リモート/ローカルの切替UI

### F-4 変換フロー直結
- チャットログ変換（Phase 3b実装済み）の出力先に「書庫へ保存」を追加

### F-5 git化バックアップ
- 書庫ディレクトリをローカルgit（private リモート）とし、配架・保存の節目でcommit/push
- 自動化の程度（保存APIフックか手動バッチか）は仕様作成時に決定

### F-6 起動統合
- start-all.batへの追加（既存4段構成に1段追加。ASCII・CRLF）

## 4. スコープ外（別工事に切り分け）
- mkb編集機能本体（挿絵挿入等・§29系譜）— 書庫は保存APIで受け皿に徹する
- chat-pwa側 read_library ツール — 索引・棚分離は接続を考慮して設計するが実装は別発令
- PDF/epubのリーダー内表示
- 私室棚のバックアップ経路
- Surface Pro 7への移設（.envパス設定により移設容易性のみ担保）

## 5. 非機能要件
- フラン電源が稼働前提（制約として明記）
- LLM不使用（モデル選定ルールの対象外）
- 認証なし。アクセス制御はtailnetで物理制御（chat-pwaと同一の考え方）
- 索引生成は数百ファイル規模で体感遅延なし

## 7. 受入基準
1. Pixel 10のmkb-reader（standalone）から書庫一覧→mkb閲覧が成立
2. txt/md/画像のリーダー内表示、PDFの端末ビューア受け渡しが成立
3. 変換成果物が書庫へ直接配架され、一覧に反映される
4. 私室棚が配信・索引に一切現れないことの機械検査（inspect項目化）
5. git化バックアップが一巡（配架→commit/push→GitHub上で確認）
6. 既存ローカルモード・GitHub Pages版が無退行
